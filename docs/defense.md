# Сценарий защиты: 8–9 минут

До выступления: открыть сервис и `/presentation`, подключить свой API-ключ,
проверить вопрос с реальной моделью, подготовить JSON. После обновления страницы
ключ нужно ввести заново. Не показывать ключ в записи экрана.

## Ход

- **0:00–0:45.** Пользователь и задача. Серия ML-запусков: выбор по качеству/времени,
  проверка истории и план следующего эксперимента.
- **0:45–1:30.** Границы MVP и архитектура. Web → LLM → MCP → расчёты → ответ.
  Отдельно пояснить request-local HTTP transport и внешний `/api/mcp`.
- **1:30–4:30.** Живая демонстрация. Учебный CIFAR-10 помечен синтетическим.
  Выбрать run-001/003/004/005 и accuracy ↑. Запросить сравнение, раскрыть MCP,
  сверить run-005=0.927, baseline run-001=0.873, разницу 0.054.
  Спросить о run-004 и проверить график: минимум validation loss на шаге 30.
  Попросить гипотезу следующего опыта: что фиксировать, что менять, как оценивать.
- **4:30–5:30.** Загрузить Iris реальных измерений. Объяснить равные accuracy=1.0
  и почему 30 validation-примеров не доказывают равенство качества моделей.
  Показать экспорт отчёта и наличие исходного скрипта.
- **5:30–6:30.** Spec-driven работа: открыть спецификацию и тесты. Показать одну
  конкретную проверку (например, запрет сравнения validation и test).
- **6:30–7:30.** Ревью и исправления из verification.md. Чем тестовый провайдер
  отличается от реальной проверки LLM.
- **7:30–8:30.** Ограничения и дальнейшая работа. Ответы на вопросы.

При отсутствии ключа допустимо показать расчётный режим, но это не полноценная
демонстрация требования LLM. Не называйте проект полностью готовым по критериям
курса, пока реальная модель не подключена и сценарий не проверен.

## Возможные вопросы

**Зачем MCP, если можно вызвать функцию?**
Инструменты имеют отдельный контракт, discovery, валидацию и стандартный transport.
Их может использовать внешний клиент; модель получает тот же набор инструментов.
Для маленького проекта прямой вызов проще, MCP здесь нужен и как требование курса,
и как граница между агентом и данными.

**Это отдельный сервер?**
Логически — MCP server из официального SDK. В production он исполняется в одном
Worker с приложением. Внутренний HTTP fetch направляется в обработчик локально,
поэтому данные запроса не нужно хранить глобально. Внешний `/api/mcp` доступен по сети
с учебными данными. Можно вынести обработчик в отдельный сервис позже.

**Где AI-логика?**
Модель интерпретирует вопрос, выбирает инструменты, обрабатывает их результаты
в нескольких шагах и формирует объяснение/гипотезу. Формулы и ранжирование не
поручаются модели. Без LLM остаётся ограниченный расчётный обзор.

**Как проверяется правильность?**
Числа — независимыми ожидаемыми значениями в тестах; контракт MCP — SDK-клиентом;
цикл агента — сценарным провайдером; объяснение — ручной сверкой ID и чисел в
журнале реального запроса. Одни unit-тесты не оценивают качество рассуждений LLM.

**Почему один seed не доказывает улучшение?**
Из-за случайности обучения и ограниченной выборки. Нужны повторные seed и подходящий
статистический анализ. История loss даёт эвристический сигнал, не причинный диагноз.

**Что может пойти не так?**
Неправильная метрика или её направление, разные протоколы оценки, малая validation,
недоступный провайдер/баланс, некорректный tool call, галлюцинация объяснения.
Система валидирует данные, ограничивает инструменты и показывает журнал; человек
всё равно проверяет вывод.

**Что сделано AI-агентом и за что отвечает автор?**
AI-агент подготовил реализацию, тесты и документы. Автор должен понимать архитектуру,
проверить критерии приёмки, подключить модель, провести демонстрацию и объяснить
компромиссы. Не утверждайте самостоятельное ручное написание всего кода.
