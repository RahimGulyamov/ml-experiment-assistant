# План реализации

Проект: «Ассистент анализа ML-экспериментов». Автор: Гулямов Рахим.

## 1. Задача и границы

Пользователь — ML-инженер, у которого накопились запуски модели на одном датасете.
Он хочет выбрать перспективный запуск, понять компромисс между качеством и временем,
проверить признаки переобучения и спланировать следующий эксперимент.

MVP: веб-интерфейс → агент LLM → MCP → проверенные расчёты → объяснение с ID запусков.
Без ключа доступен отдельный расчётный обзор через тот же MCP; это не LLM-режим.
Не входят: обучение моделей, запуск произвольного кода, продакшен-рекомендации,
авторизация пользователей, облачное хранение, интеграции MLflow/W&B.

## 2. Этапы и контрольные точки

| Этап | Результат | Проверка перед следующим этапом |
| --- | --- | --- |
| Постановка | OpenSpec, сценарии, требования | Каждое требование имеет критерий приёмки |
| Данные | Строгая схема, JSON/CSV, учебный набор | Дубликаты, NaN, несовместимые группы отклоняются |
| Аналитика | Ранжирование, сравнение, диагностика | Ручные ожидаемые значения в unit-тестах |
| MCP | SDK-сервер, HTTP endpoint, клиент | initialize, tools/list, tools/call настоящим SDK |
| Агент | Ограниченный цикл tool calling | Модель использует MCP; ошибки не маскируются |
| Интерфейс | Таблица, график, импорт, чат, отчёт | Основной сценарий и мобильная ширина |
| Поставка | README, HTML-слайды, CI, хостинг | Чистая установка, typecheck, тесты, build |
| Ревью | Отчёт о дефектах и исправления | Повторные проверки после исправлений |

## 3. Последовательность реализации

1. Определить формат запуска: ID, имя, датасет, split, эксперимент, метрики,
   параметры и необязательная история train/validation loss.
2. Сделать воспроизводимый синтетический набор с заведомым переобучением,
   эффективной моделью и неудачным запуском. Пометить происхождение данных.
3. Реализовать загрузку до 2 MiB и 200 запусков, только конечные числа,
   уникальные ID, ограниченную длину полей и историй. Ошибка указывает поле.
4. Сравнивать только одну группу experiment/dataset/split. Направление метрики
   пользователь задаёт явно. Показывать абсолютную и относительную разницу.
5. Сделать MCP-инструменты list_runs, compare_runs, inspect_run, diagnose_run.
6. Предоставить Streamable HTTP `/api/mcp` с демонстрационными данными. Внутри
   запроса агента использовать такой же HTTP transport через request-local fetch,
   привязанный к загруженному набору. Не смешивать данные разных пользователей.
7. Реализовать OpenAI-compatible Chat Completions tool calling, лимиты шагов,
   времени и контекста. Ключ передавать на один запрос, не сохранять.
8. Добавить видимый журнал MCP, ограничения выводов и экспорт Markdown-отчёта.
9. Сделать компактный интерфейс исследовательского инструмента на русском.
10. Подготовить презентацию на 7–9 минут, сценарий демонстрации и ответы.
11. Пройти негативные сценарии и исправить найденные ошибки.
12. Опубликовать сайт и публичный GitHub-репозиторий при доступной авторизации.

## 4. Готовность к сдаче

Локальная поставка считается проверенной после успешных тестов, typecheck и build.
Для полной сдачи дополнительно нужны рабочая модель/ключ, проверка реального LLM,
публичная ссылка на репозиторий, доступ преподавателя к сайту и участие в воркшопе.
Никакая локальная проверка не заменяет эти внешние условия.
